# Live2D 模型资源站鉴权与数字人命名设计

日期：2026-04-14
项目：digital-human

## 1. 目标

本次设计解决两个明确目标：

1. 将 `https://live2d.zhuyougu.cn` 从旧的 H5 展示页改为纯模型资源存放域名。
2. 为 Live2D 模型资源增加访问鉴权，只有携带现有业务登录 token 的客户端才能访问模型文件。
3. 确认数字人名称为 **安禾**，后续在小程序与相关文案中统一使用。

## 2. 非目标

本次不包含以下内容：

- 不重做 Live2D 渲染方案本身
- 不引入新的独立账号体系或新的资源访问 token 体系
- 不实现短期签名 URL
- 不在本次设计中处理模型资源防下载到“绝对无法提取”级别的问题

说明：前端可见资源无法做到绝对防提取，本次目标是做到“必须登录、默认不可匿名直链、结构上不再公开暴露”。

## 3. 推荐方案

采用 **独立资源域名 + 复用现有登录 token 鉴权** 的方案。

### 3.1 方案概述

- 保留 `live2d.zhuyougu.cn` 作为独立域名
- 该域名不再提供 H5 页面，只提供模型静态资源
- 小程序访问模型文件时携带现有业务登录 token
- 资源服务端校验 token，校验通过后返回模型文件
- 禁用目录浏览与默认首页，避免资源清单被匿名查看

### 3.2 选择原因

相比“全部走 gateway 代理”，独立资源域保留了更清晰的职责边界与更好的静态资源承载能力。

相比“签名 URL”，复用现有登录 token 更简单，和当前系统一致，前后端改动都更小，适合作为第一阶段方案。

## 4. 备选方案与取舍

### 方案 A，独立资源域 + token 鉴权（推荐）

优点：
- 结构清晰
- 便于后续单独做缓存、限流、资源迁移
- 前端只需在模型请求上补 token
- 不破坏现有业务网关结构

缺点：
- 需要在资源域前增加一层鉴权逻辑
- 静态资源服务不能再是完全裸 nginx 目录直出

### 方案 B，全部改走 gateway

优点：
- 鉴权逻辑最统一
- 后端权限控制集中

缺点：
- gateway 承担静态资源流量
- 资源路径会混入业务 API 命名空间
- 后续做静态资源优化不够灵活

### 方案 C，签名 URL

优点：
- 防直链更强
- 可设置短时失效

缺点：
- 实现复杂度明显升高
- 需要额外签发与续期逻辑
- 当前阶段属于过度设计

## 5. 架构设计

## 5.1 域名职责

### `live2d.zhuyougu.cn`
- 仅承载模型资源
- 不承载 H5 页面
- 不提供目录浏览
- 不暴露资源列表接口

### `gateway.zhuyougu.cn`
- 继续负责业务 API 与现有登录体系
- 其签发的登录 token 作为模型资源访问凭证

## 5.2 资源访问流程

1. 小程序用户完成正常登录
2. 前端拿到现有登录 token
3. `medical-mp` 在请求 `.model3.json`、`.moc3`、纹理、动作、表情、物理文件时附带 token
4. `live2d.zhuyougu.cn` 对 token 进行校验
5. 校验通过，返回对应资源
6. 校验失败，返回 `401` 或 `403`

## 5.3 前端改造边界

前端只做以下改造：

- 为 Live2D 资源请求统一附带登录 token
- 在模型资源请求失败时区分未授权与普通加载失败
- 将数字人显示名称统一为 **安禾**

前端不做以下事情：

- 不保存第二套固定资源密钥
- 不生成签名 URL
- 不实现资源清单探测逻辑

## 5.4 服务端改造边界

服务端需要满足：

- 资源域能读取模型目录中的静态文件
- 对请求头中的 token 做校验
- 拒绝匿名访问
- 默认关闭目录浏览、默认首页和旧 H5 路由

实现上可以是两类落地方式之一：

1. **资源域前置鉴权层**
   - 例如通过 OpenResty / Nginx `auth_request` / 反向代理到鉴权接口
2. **由业务服务提供鉴权后文件返回**
   - 资源域仅做转发，鉴权和文件返回由后端服务完成

在不增加不必要复杂度的前提下，优先选更贴近现有部署结构的方式。

## 6. 资源范围与约束

允许访问的资源类型应覆盖当前 Cubism 4 模型运行所需文件：

- `.model3.json`
- `.moc3`
- `.png`
- `.physics3.json`
- `.motion3.json`
- `.exp3.json`
- 其他模型运行必需的附属 JSON / 二进制资源

约束：

- 禁止目录索引
- 禁止匿名列目录
- 禁止保留旧 `index.html`
- 不要求隐藏资源文件名本身，但要求访问前必须先通过鉴权

## 7. 安全设计

## 7.1 认证原则

- 模型资源访问认证复用现有业务登录 token
- 服务端只信任服务端校验结果，不信任前端自行声明身份
- 对无 token、空 token、无效 token、过期 token 一律拒绝

## 7.2 安全边界说明

该方案可以实现：

- 防匿名访问
- 防未登录直链访问
- 防公开目录遍历

该方案不能绝对阻止：

- 已登录客户端在本地拿到资源后被二次导出
- 通过抓包分析已授权请求后的资源重放

如果未来需要更高防护等级，再叠加：

- 短期签名 URL
- 客户端设备绑定
- 请求频率限制
- Referer / User-Agent / 来源特征校验

## 8. 错误处理

资源域对外行为统一如下：

- 未携带 token：`401 Unauthorized`
- token 无效或过期：`403 Forbidden` 或 `401 Unauthorized`，实现时保持一致即可
- 文件不存在：`404 Not Found`
- 服务内部错误：`500 Internal Server Error`

前端表现：

- 若是 `401/403`，日志明确记录为“模型资源未授权”
- 若是 `404`，日志明确记录为“模型资源缺失”
- 若是其他错误，按通用加载失败处理

## 9. 命名设计

数字人最终名称定为：**安禾**

命名原因：

- “安”对应安抚、安心、安定，契合护士陪伴与医疗场景
- “禾”降低生硬感，让名字更温和、自然、像真人
- 听感专业但不冰冷，适合数字护士角色

使用建议：

- 页面展示名统一为“安禾”
- 若后续补角色设定，可采用“智能护士安禾”或“安禾护士”作为扩展叫法
- 对外文案避免同时混用多个名字，保持记忆点一致

## 10. 测试设计

### 前端验证

- 已登录状态下，模型可完整加载
- 未登录状态下，模型资源请求失败且报未授权
- token 过期后重新进入页面，模型请求失败行为符合预期
- 名称展示处统一显示“安禾”

### 服务端验证

- 不带 token 请求模型文件返回 `401/403`
- 带合法 token 请求模型文件返回 `200`
- 非法路径不能列目录
- 旧 H5 首页访问不再返回原页面

### 集成验证

- 微信开发者工具中模型可正常加载
- 真机中模型可正常加载
- 模型依赖的纹理、动作、表情、物理文件都能随主模型成功拉取

## 11. 分阶段实施建议

### 第一阶段

- 移除旧 H5 页面入口
- 将 `live2d.zhuyougu.cn` 改为模型资源域
- 接入基于现有登录 token 的访问鉴权
- 小程序资源请求补 token
- 统一名称为“安禾”

### 第二阶段（可选增强）

- 增加访问日志与失败审计
- 增加限流
- 增加更细粒度的资源路径控制
- 如有必要，再升级为签名 URL

## 12. 实施范围判断

本设计范围适合作为单个实现计划执行，不需要继续拆成多个独立项目。

建议按以下顺序实施：

1. 资源域改造与旧 H5 下线
2. 资源鉴权接入
3. 小程序请求头改造
4. “安禾”命名统一
5. 联调与真机验证
