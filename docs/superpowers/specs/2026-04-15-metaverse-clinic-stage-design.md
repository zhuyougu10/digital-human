# 陪伴型元宇宙诊室（单主舞台）设计稿

日期：2026-04-15  
项目：`medical-mp`  
状态：已与主人确认（可进入 implementation planning）

---

## 1. 目标与定位

将当前 `medical-mp` 从“传统多页面医疗小程序”升级为“数字人主导的沉浸式诊室舞台”。

核心目标：
- 数字人（安禾 / Wariza）成为全程视觉与交互主角
- 主链路在单一舞台内完成，避免传统页面跳转打断体验
- 问诊输入统一支持：**打字 / 说 / 点气泡**
- 视觉风格升级为：暗色沉浸 + 玻璃材质 + 电影级字幕

---

## 2. 已确认决策

### 2.1 架构路线（主人已选）
- 采用 **方案 2：单主舞台 + 系统抽屉**

解释：
- 主链路（问诊、分诊、医生推荐、预约确认）在一个舞台中连续完成
- 非主链路（档案、日程、设置、协议）放入抽屉或次级页
- 在沉浸感与工程可控性之间取平衡

### 2.2 输入方式（主人已确认）
统一三入口：
- 打字
- 说（语音）
- 点气泡

约束：三入口必须收敛到同一问诊状态机，不允许形成三套分裂业务流程。

---

## 3. 信息架构

### 3.1 顶层结构
- 主页面：`Stage`（诊室舞台）
- 主链路场景：
  1. 入场欢迎（Idle）
  2. 症状采集（Collecting）
  3. 追问澄清（Questioning）
  4. 分诊建议（Triage Result）
  5. 医生推荐（Doctor Flow）
  6. 预约确认（Booking Confirm）

- 次级功能（抽屉/次级页）：
  - 医疗档案
  - 预约日程/历史
  - 账号与设置
  - 协议与帮助

### 3.2 视觉层级模型（L0~L5）
- L0 背景层：动态环境光（时段可切）
- L1 数字人层：安禾 Live2D（常驻）
- L2 字幕层：电影级提词字幕
- L3 交互层：动态气泡与快捷选项
- L4 系统浮层：医生卡片流、预约确认板、抽屉
- L5 反馈层：聆听波纹、加载、错误提示

---

## 4. 三大核心场景布局

### 4.1 场景 A：私人诊室前台（入场）
- 去除传统九宫格与 TabBar 主导
- 中上部：安禾主视区（idle motion）
- 中部：欢迎字幕（如“早上好，今天感觉怎么样？”）
- 中下部：悬浮入口（档案 / 日程）
- 底部：Input Dock（三入口并行，语音视觉权重最高）

### 4.2 场景 B：情境问诊舱（收集中）
- 背景整体变暗，焦点收束
- 右侧可显示轻量症状关联可视区（腹部高亮等）
- 底部为连续问询字幕（非 IM 长气泡）
- 中下部动态候选气泡（可点选）
- 输入仍是打字/语音/点气泡三并行

### 4.3 场景 C：全息推介板（分诊与挂号）
- 安禾缩至左上角陪伴位，持续播报建议
- 中央显示医生 Cover Flow 卡片流（可左右滑）
- 卡片信息：医生、科室、擅长、号源、立即预约
- 底部 CTA：`直接预约` / `查看其他医生`

## 5. 视觉与动效规范

### 5.1 视觉基调
- Dark Mode 优先（深蓝灰，不纯黑）
- 玻璃拟态（Glassmorphism）
- UI 不抢数字人和字幕焦点

### 5.2 建议色板（首版）
- 背景渐变：`#0B1220` → `#111B2E`
- 主强调：`#56C6E6`
- 状态高亮：`#7CF0D6`
- 主文本：`#EAF4FF`
- 次文本：`#A9B8CC`
- 玻璃卡片：`rgba(255,255,255,0.10)`
- 玻璃边框：`rgba(255,255,255,0.24)`

### 5.3 动效规则
- 禁止系统默认 slide-in 转场
- 统一 `Fade + Scale`，必要时极小位移
- 场景切换：220ms~320ms
- 高频点击反馈：120ms~180ms

## 6. 工程拆分（可执行）

### 6.1 页面与组件
新增（或重构）主舞台：
- `pages/stage/index.vue`

核心组件建议：
- `StageBackground`
- `WarizaActor`
- `CinematicSubtitle`
- `InputDock`
- `ChoiceBubbles`
- `SymptomOverlay`
- `DoctorFlowPanel`
- `SystemDrawer`
- `StageToast`

### 6.2 状态机
`idle -> collecting -> questioning -> triage_result -> doctor_flow -> booking_confirm`

补充分支：
- interrupted
- fallback_input
- retry
- booking_done

约束：
- 所有输入统一经 `dispatchInput()`/`handleUserIntent()`
- UI 只消费统一状态源，不各自维护分叉流程

### 6.3 兼容边界（不改契约）
- SSE、TTS、Live2D 继续复用现有能力
- 医生/预约 API 契约不改
- 本轮重点在交互壳层与视觉重构

---

## 7. 分阶段落地策略

- Phase 1：搭建 Stage 壳与静态三场景切换（假数据）
- Phase 2：接入真实问诊流（SSE/TTS）
- Phase 3：接入医生推荐与预约确认浮层
- Phase 4：抽屉系统与动效收口

---

## 8. 非目标与风险

非目标：
- 不改后端协议
- 不引入无关大型依赖
- 不做业务能力扩展

风险：
- 单舞台状态复杂度上升
- 动效与性能平衡（尤其小程序端）
- 旧页面并存期可能出现导航一致性问题

缓解：
- 严格状态机边界
- 分阶段逐步替换
- 每阶段单独构建验证与真机体验回归

---

## 9. 验收标准（设计层）

设计验收通过需满足：
1. 用户首屏能明确感知“数字人主导”
2. 主链路无传统多页面打断
3. 输入三入口并行且行为一致
4. 医生推荐与预约在舞台内闭环
5. 视觉统一为沉浸暗色玻璃风，且中文可读性优秀
