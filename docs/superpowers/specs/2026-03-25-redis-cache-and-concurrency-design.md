# Redis 缓存与高并发支撑设计

> 日期：2026-03-25
> 状态：已确认（Draft v1）
> 范围：缓存优先，高并发保护为辅助

## 1. 背景与目标

项目当前已经具备 Redis 基础设施与公共模块 `medical-common-redis`，但业务层尚未形成统一的缓存与高并发支撑策略。随着系统进入联调与真实运行态阶段，主要压力集中在以下几个方面：

- 医生、科室、排班等读多写少接口频繁回源数据库
- 知识检索链路对 embedding / 检索资源消耗较高
- 预约创建在高并发场景下存在重复提交与热点号源竞争问题
- AI 会话存在短生命周期状态，但不适合全部走数据库存取

本次 Redis 方案目标是：

- **优先提升读性能**：为热点查询建立统一缓存层
- **辅助支撑高并发**：为预约链路提供防重复与短期状态控制
- **保持实现简单稳定**：采用“旁路缓存 + TTL + 写后删缓存”策略

## 2. 设计原则

### 2.1 缓存优先，高并发保护辅助

Redis 本次主要承担：

- 查询缓存
- 热点保护
- 短期状态

不承担：

- 预约主事务一致性（仍由 MySQL + Seata 保证）
- 长期业务真相数据存储

### 2.2 一致性优先级

采用 **旁路缓存（Cache Aside）**：

- 读：先查 Redis，未命中再查 DB 并回填
- 写：先写 DB，成功后删除缓存

这是当前阶段最稳妥的方案，允许极短时间的缓存脏读窗口，但实现和运维成本最低。

### 2.3 分类治理

不同业务数据使用不同 TTL 和删除策略：

- 静态/半静态数据：较长 TTL
- 高频变化数据：短 TTL + 写后删缓存
- 防重复/锁类数据：超短 TTL

## 3. 方案选型

### 方案 A：旁路缓存 + TTL + 写后删缓存（推荐）

优点：

- 简单稳定
- 与现有业务代码和微服务边界最兼容
- 不需要先重构读写模型

缺点：

- 会存在极短脏读窗口

### 方案 B：旁路缓存 + 关键路径延迟双删

优点：

- 能进一步降低脏读概率

缺点：

- 实现复杂度更高
- 当前阶段收益不明显

### 方案 C：缓存预热 + 主动刷新 + 多级缓存

优点：

- 性能上限高

缺点：

- 过度设计，不适合当前项目阶段

**结论：采用方案 A。**

## 4. 业务范围与优先级

### 第一层：读缓存（优先落地）

#### doctor-service

- 医生列表
- 医生详情
- 科室列表

#### doctor-service（短 TTL）

- 排班号源查询

#### knowledge-service

- 知识检索热点结果

### 第二层：高并发辅助能力

#### appointment-service

- 预约防重复提交
- 热点号源短期状态
- 请求级短期限流辅助状态

### 第三层：会话短态

#### ai-service

- AI 会话短生命周期状态
- SSE / 异步任务短态

## 5. 各服务设计

### 5.1 doctor-service

#### 缓存对象

- 医生列表：`doctor:list:{page}:{size}:{keyword}`
- 医生详情：`doctor:detail:{doctorId}`
- 科室列表：`department:list`
- 号源列表：`schedule:slots:{doctorId}:{date}`

#### TTL 建议

- 医生列表：`10-30 min`
- 医生详情：`10-30 min`
- 科室列表：`30-60 min`
- 号源列表：`30-120 s`

#### 删除策略

- 医生资料更新后删除 `doctor:detail:{doctorId}` 与相关列表缓存
- 科室变更后删除 `department:list` 及相关医生列表缓存
- 排班生成、预约占号、取消释放后删除对应 `schedule:slots:{doctorId}:{date}`

### 5.2 knowledge-service

#### 缓存对象

- 知识检索结果：`knowledge:search:{kbId}:{queryHash}:{topK}`

#### TTL 建议

- `5-15 min`

#### 设计约束

- 只缓存热点查询结果，不缓存底层 embedding 向量
- 查询 key 必须做 query 归一化 + hash，避免 key 过长
- 空结果也缓存短 TTL，防止缓存穿透

### 5.3 appointment-service

#### 不优先做重缓存的数据

- 预约详情/列表不作为第一优先缓存目标

原因：

- 写频率更高
- 状态变化更敏感
- 价值不如医生/排班查询缓存高

#### 高并发辅助能力

- 防重复提交 key：`appointment:dedup:{patientId}:{slotId}`
- 超短 TTL：`10-60 s`

创建预约前：

- `SETNX` 成功才继续主流程
- 失败则快速返回“请勿重复提交”

注意：

- Redis 幂等键只是前置保护
- 真正一致性仍以现有 Seata 主链路为准

### 5.4 ai-service

#### 仅做短态缓存

- `ai:session:{sessionId}`
- 临时上下文、流式短态、任务标记

#### 不建议当前阶段做的事

- 不建议直接缓存模型完整回复
- 不建议把复杂 AI 长期状态直接搬进 Redis

## 6. 缓存模式设计

统一采用 Cache Aside：

### 读流程

1. 先查 Redis
2. 命中直接返回
3. 未命中查 DB
4. 查到后回填 Redis
5. 查不到时缓存空值（短 TTL）

### 写流程

1. 先写 DB
2. DB 成功后删除对应缓存 key

### 为什么不用写穿/写回

- 当前项目以业务可控性优先
- 写穿/写回需要更复杂的一致性治理
- 对当前毕设规模没有明显收益

## 7. TTL 与 Key 规范

### 7.1 TTL 建议

| 类型 | TTL |
|------|-----|
| 医生列表/详情 | 10-30 min |
| 科室列表 | 30-60 min |
| 排班号源 | 30-120 s |
| 知识检索结果 | 5-15 min |
| 预约防重复 key | 10-60 s |
| AI 会话短态 | 5-30 min |

### 7.2 TTL 抖动

所有缓存建议增加随机抖动，避免同一批 key 同时过期。

例如：

- 基础 TTL = 600s
- 实际 TTL = `600 + random(0,120)`

### 7.3 Key 规范

- 统一使用小写前缀 + 冒号分段
- 业务域优先：`doctor:*`、`schedule:*`、`knowledge:*`、`appointment:*`、`ai:*`
- 检索类 key 中 query 必须 hash 化

## 8. 高并发支撑设计

### 8.1 重复提交保护

在 `appointment-service.createAppointment()` 前增加 Redis 防重：

- key：`appointment:dedup:{patientId}:{slotId}`
- value：请求唯一标识或固定占位值
- TTL：`30 s` 左右

### 8.2 热点号源支撑

Redis 不负责真正扣减号源，只负责：

- 热点查询缓存
- 热点快速失败辅助状态

真实扣减仍在 `doctor-service` + Seata 主链路完成。

### 8.3 穿透 / 击穿 / 雪崩防护

- 空值缓存：防穿透
- TTL 抖动：防雪崩
- 热点 key 构建锁：防击穿

## 9. 实施建议

### 第一批（推荐立即落地）

- doctor 列表/详情缓存
- department 列表缓存
- schedule slots 短 TTL 缓存
- appointment 防重复提交 key

### 第二批

- knowledge 检索结果缓存
- AI 会话短态缓存

### 第三批

- 视运行态再决定是否对预约列表、管理端统计查询做更多缓存

## 10. 测试策略

### 单元测试

- 缓存命中/未命中逻辑
- 写后删缓存逻辑
- 重复提交防护逻辑

### 集成测试

- Redis 命中后不再访问 DB
- 更新医生/排班后缓存被删除
- 重复预约请求被 Redis 快速拒绝

### 运行态验证

- Docker Compose 环境下执行热点查询多次，验证命中率提升
- 人工观察 Redis key 生命周期与删除行为

## 11. 风险与约束

- 当前方案不追求绝对强一致缓存
- 对于排班号源这类高变化数据，只能接受“短 TTL + 写后删缓存”的轻微脏读窗口
- 如果后续出现多服务共同更新同一类缓存对象，需要重新梳理失效边界

## 12. 结论

本次 Redis 方案明确采用：

- **缓存优先**
- **高并发保护辅助**
- **旁路缓存 + TTL + 写后删缓存**

这条路线能以最低复杂度最快拿到系统收益，同时和当前已经完成的 Seata、Sentinel、RabbitMQ 方案保持职责边界清晰：

- Seata：同步强一致
- RabbitMQ：副作用异步化
- Redis：热点查询加速 + 高并发辅助状态
